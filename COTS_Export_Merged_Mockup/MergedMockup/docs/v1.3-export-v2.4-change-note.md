**Date** 27 August 2026
**Status** Draft for review. Not approved.

**Sources**
- `COTS_Export_End_to_End_Workflow_v2.3` (26 August 2026) — authoritative for the Export process,
  its sequence, statuses, fields, rules and open items
- Export mock-up **v2.4** and its change note of 27 August 2026 — authoritative for the Export
  screens, their layout, fields and navigation
- `COTS_Integrated_Workflows.md` (WF-INT-01 … WF-INT-14) — authoritative for how Core and Shared are

## What this version is

An **update** to the existing integrated mockup, not a rebuild. Core and Shared are untouched, the
Export prototype is untouched, the application shell and every existing route are preserved, and
every Export destination key that worked in v1.2 still resolves.

What changed is the Export contribution the mockup reaches, and the integration layer's model of the
Export process — which had to change, because the process it modelled no longer exists.

## The defect this version fixes first

**The Export bridge was pointing at a build that is no longer delivered.** Every candidate path in
`vite.config.ts` named `COTS_Export_Mockup_v1.1`. That folder is not on the delivery any more — the
Export contribution has moved through v2.0 to v2.4 — so the build logged *"the Export portable build
was not found"* and every Export screen in the integrated mockup showed its not-found state.

The candidates now prefer **v2.4**, then v2.0, and keep the v1.1 paths last, so a machine with an
older checkout still runs rather than failing outright.

The session hand-over needed no change, and this was checked rather than assumed: Export v2.4 uses the
same `sessionStorage` key and the same five demo accounts, with the same ids, usernames and roles.
`src/integration/session.ts` records the check, because a silent change to either would not break the
build — it would quietly reintroduce the second sign-in that v1.1 removed.

## The comparison that drove the rest

| | v1.2 (against workflow v2.0) | v1.3 (against workflow v2.3) |
|---|---|---|
| Export process | 16 phases | **23 phases** — v2.3 inserts seven ahead of the sixteen and renumbers them 08–23 |
| Export contribution | v1.1 portable build, **absent from disk** | **v2.4** portable build |
| Export destinations | 14, a flat hand-maintained list | **33** — 23 phases and 10 screens serving the whole process, derived from one model |
| Screens removed | — | **none.** All 14 v1.2 destinations still exist in v2.4 and all 14 keys still resolve |
| New Export screen families | — | the whole origin-side intake chain (`/sourcing/**`), origination, allocation, movement, close-out, freight rates, advance payments |
| Export navigation | one tile into the springboard | a module landing page, a grouped menu, a phase rail, previous/next |
| Phases 01–02 | not built anywhere | built at mock-up v2.1–v2.4 |

The delta is **additive**. Nothing the Export contribution offered in v1.1 was withdrawn in v2.4, which
is why no v1.2 link had to die.

## The twenty-three phases, and where they are

`src/integration/exportProcess.ts` is new and is the centre of this version: one ordered model of the
twenty-three phases in the workflow's own sequence, each carrying its exact name, the section it is
grouped under, the Export v2.4 screens that serve it, the owner the workflow names *or the fact that
it names none*, the statuses it states, the Core and Shared capabilities the phase uses, and every
`[OPEN]`, `[ASSUMPTION]`, `[PROPOSED]` and `[AS-IS]` item that belongs to it.

The six UI sections partition 1–23 **in order**, and are presentation only:

| Section | Phases |
|---|---|
| Planning & Intake | 01–07 — seasonal purchase plan, budget, funds, purchase agreement, receiving location, material receipt, warehouse receipt |
| Commercial & Contract | 08–12 — opportunity, deal, contract in SAP, cross-functional review, quality and tags |
| Allocation & Execution | 13–14 — stock allocation and cargo readiness, country-specific prerequisites |
| Logistics & Clearance | 15–18 — freight, pre-clearance and regulatory, movement and stuffing request, container inspection and stuffing |
| Shipping & Documents | 19–21 — shipping instructions, draft/confirmed/original documents, final assembly and charges |
| Finance & Close-Out | 22–23 — bank submission and payment, delivery and close-out |

Three properties are **enforced**, not asserted in prose:

- the phases run 1…23 with no gap, no duplicate key, and each section contiguous — by an invariant
  that throws at module load, because a wrong phase order shown to a business reviewer is the one
  failure this layer exists to prevent;
- every screen path exists in the Export contribution's own `App.tsx` — by `walk.mjs`, which checked
  **69 distinct paths against 62 route patterns** on the last run;
- a field the mock-up or the spreadsheet introduced is typed as such and rendered as such, so it can
  never be presented as a field the workflow states.

## The one new integration finding

**The seven phases v2.3 inserted have no integrated workflow.**

`WF-INT-01` … `WF-INT-14` were written against the sixteen-phase process. The origin-side intake
chain is covered by none of them, so for phases 01–07 there is no source that says which Core or
Shared capability the work uses.

**No WF-INT workflow has been invented for them.** The absence is stated on the journey map as
`INTAKE_INTEGRATION_GAP`, and the capability links those phases would need are all marked *proposed*
and rendered differently from a stated binding.

It is blocked by the workflow's own **G-31 / D-23** — whether export owns the origin-side intake chain
at all, or sourcing does. §2.2 excluded it; v2.3 brings it in on a business instruction of 26 August
2026 and records the reversal rather than resolving it. Until that is settled, which module's
capabilities these phases should reach is not answerable either.

## Where the sources disagree, and what was done about it

Both are recorded on screen rather than settled, because settling either is a business decision.

1. **The Export mock-up's own phase model is still the sixteen phases of workflow v2.0.**
   `export-process-mockup/src/domain/workflow.ts` holds `WF01`…`WF16` and its process-map screen is
   captioned "the sixteen phases". The mapping is exact and additive — v2.0's phase *n* is v2.3's
   phase *n* + 7 — and is carried as `mockupPhaseId`. **Nothing in the Export contribution was
   changed.** The Export team may want to renumber its own model; that is their call.

2. **Workflow v2.3 §16.1 says phases 01 and 02 have no screen. They do.** v2.3 was written on
   26 August; mock-up v2.1 built the plan, v2.2 rebuilt it to `Export Plan V1.xlsx`, v2.3 gave the
   budget its rules and v2.4 reshaped funds and the purchase agreement. The workflow governs
   behaviour and the mock-up governs presentation, so the screens are recorded as present and the
   statement is marked superseded rather than contradicted in silence.

## Unresolved items preserved, and one class of error corrected

152 unresolved items are carried onto the phases they belong to, plus six that belong to the process
rather than to any one phase — including two of the twenty-two §14 decisions (**D2**, **D-18**) that
were reachable nowhere in the mockup before.

An independent review of the first draft of this version found the mockup doing exactly what it was
built to prevent, in three places. All three are corrected:

- **Phase 20 presented the `[PROPOSED]` six-state document model as a status the workflow states**,
  with an ordering, and dropped the seven `[AS-IS]` status sets it would replace. The seven facts are
  restored; the proposed model is labelled *proposed, not stated*; and `statuses` is now typed so the
  distinction cannot be lost by editing a string.
- **Two `[AS-IS]` statements were tagged `PROPOSED`**, because the model had no `AS-IS` member — so
  observed practice in a live system was rendered as "recommended and not agreed", which inverts the
  risk rather than mislabelling it. `AS-IS` is now a tag in its own right.
- **`fields` was captioned "the workflow's own words"** and carried mock-up-derived fields for phases
  01–04 while omitting three that §6.3 states. Provenance is now typed per field and shown, and the
  three §6.3 fields are back with a note that v2.4 stopped capturing them.

A fourth error, in the same class: the phase labels first added to `journey.ts` were generated from
each step's link target, and five of twenty-two were wrong wherever an Export screen serves more than
one phase — custody, free days, the stuffing report, the charges and close-out. The label is now
derived from the process model through an explicit `phaseKey`, so the number and the name cannot
disagree with `exportProcess.ts`, and six links were retargeted to the phase that owns the work. A
side effect: phase 23 is now reachable from the journey map, which it was not.

## What this version does not claim

- **No progress.** Nothing in this layer knows how far a real shipment has got. The phase rail shows
  a *position*, never a visit record.
- **No invented rule.** No status the workflow does not state, no owner it does not assign, no
  approval, validation or country rule.
- **Nothing changed inside Export, Core or Shared.** Verified by a full tree diff: all three source
  trees are byte-identical to before this change.

## What was checked

- **`npx tsc -b`** — clean.
- **`npm run build`** — clean, and the bridge now resolves to the v2.4 portable build (the
  "not found" warning is gone).
- **`node walk.mjs`** — **186 of 186 routes** render with no console error (integration 45, Core 71,
  Shared 70); **6 of 6** module-access cases; **3 of 3** menus by privilege; **4 of 4** model
  comparisons, including **69 of 69** Export paths resolving against the Export contribution's own
  route table. Exits non-zero on any failure, so it can be a gate.
- **The frame, in a browser.** All 33 destinations frame the v2.4 build and it renders; all 23 phases
  open **their own** Export route with the Core session carried and no second sign-in; all 40
  capability targets resolve to a real Core or Shared screen.
- **Accessibility.** The phase rail's targets are 24px (they were 6px), its bars are 4.95:1 and
  6.76:1 against white (they were 1.35:1 and 2.38:1), position is in the accessible name rather than
  carried by colour alone, and no tooltip overrides a control's own name. The bridge screen has real
  headings and sets the document title per phase.
- **Responsive.** No page-body horizontal scroll at any width from 480px to 1920px. At 390px the new
  screens overflow by exactly the same 48px as the untouched Core `/home`, which is the Core app
  bar's own pre-existing behaviour.
- **No regression.** Core routes 88, Shared routes 72 — identical before and after. 173 route pairs
  in `App.tsx`, of which exactly one changed (`/export` renders the landing page instead of
  redirecting). No file deleted anywhere.

## Open for decision

Nothing in this note requires a decision to run the mockup. These are the questions it puts in front
of a reviewer:

1. **G-31 / D-23** — does export own the origin-side intake chain, or does sourcing? Until this is
   answered, phases 01–07 have no integration design and their capability links stay proposals.
2. **The Export mock-up's sixteen-phase model** — should `domain/workflow.ts` and the process-map
   screen be renumbered to v2.3's twenty-three? That is a change to the Export contribution and was
   not made here.
3. **Whether the four new components belong in the Core design system**, and whether the three new
   colours should be promoted into the Core token set. See the ADR.
4. **Whether `walk.mjs` is the project's only gate.** It is the only automated check this package has;
   there is no test runner.
