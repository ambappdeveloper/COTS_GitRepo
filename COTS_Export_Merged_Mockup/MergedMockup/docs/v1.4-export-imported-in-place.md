# Integrated mockup v1.4 — Export imported in place, and the frame removed

**Date** 27 August 2026
**Status** Draft for review. Not approved.

**Supersedes** the iframe bridge that stood from v1.1 to v1.3.

---

## What changed, in one sentence

Export was the one contribution this application did not compile — it was a portable HTML build in an
`<iframe>`, with the Core session handed between two origins so nobody had to sign in twice. It is now
imported from its own sources and rendered inside the one Core shell, exactly as Core and Shared have
been since v1.2.

## Why it is worth doing

The frame was a reasonable answer to a real constraint, and it cost four things that no amount of
polish on the bridge could fix:

1. **A third bar inside a frame.** The Export application drew its own app bar, its own module
   drawer, its own home control and its own account menu, inside a window that already had all four.
   The v1.2 review called this out and v1.3 could not fix it.
2. **A session carried between origins.** One `sessionStorage` key, written before the frame loaded,
   re-written whenever the account or the country changed, and cleared on sign-out — all to avoid a
   second sign-in that only existed because there were two applications.
3. **Three loading modes, two of which worked.** Off a folder and on the dev server the frame loaded;
   under `vite preview` it could not resolve its own relative path and fell back to a dev server that
   was usually not running. The route check passed regardless, because it checked the wrapper rather
   than the frame's contents.
4. **No cross-module links from inside an Export screen.** A frame cannot link out to `/c7/register`.
   Everything the integration layer wanted to say about a phase had to be said in a strip above the
   frame rather than beside the work.

## What it took, and what it did not

**No dependency was upgraded, and that was the surprise.** Export's `package.json` names React 19,
react-router 7, Vite 8 and TypeScript 6. Its *source* uses no API from any of them that this
application's React 18 and react-router 6 do not have — no `useActionState`, no `useOptimistic`, no
`use()`, no `RouterProvider`, no loaders or fetchers. That was checked before any work started rather
than assumed, and it removed the single largest risk in the change.

**Exactly one Export module is substituted:** `auth/AuthContext.tsx`, redirected by `vite.config.ts`
to `src/export/ExportAuthBridge.tsx`. Twelve Export page files call `useAuth()`, and Export's own
implementation authenticates against its demo accounts in `sessionStorage` — which is what produced
the second sign-in in the first place. The bridge returns the person who signed in at the Core screen.
Remove that one line and the Export prototype authenticates exactly as it does standalone.

**Export's `Shell` and its `global.css` needed no substitution at all.** Both are imported by Export's
own `App.tsx` and by nothing else, and this application mounts Export's routes itself rather than
using that file, so neither is ever loaded.

**No file inside the Export contribution was changed.** Same guarantee Core and Shared have had since
v1.2 — and the same guarantee that still holds for them.

## Export keeps its own paths

This is rule 1 at the head of `src/App.tsx` applied to the third prototype. Core keeps `/c1…/c12`,
Shared keeps `/s01…/s11`, and Export now keeps `/contracts`, `/shipments`, `/sourcing/plans`,
`/movement/leg/:id` and the rest — sixty-nine addresses, none of which collides with Core's or
Shared's. Every internal link inside the Export prototype resolves without one of its files being
touched.

Two addresses are this layer's own:

| Address | What it is |
| --- | --- |
| `/export` | The module landing page — the twenty-three phases in order |
| `/export/springboard` | Export's springboard. Export calls it `/`, and this application's `/` is the Core home; two prototypes cannot both own the root |

And **`/export/<key>` is kept as a redirect.** Every destination key any version since v1.1 linked to
— in walkthroughs, review notes, bookmarks and the journey model — still lands on the right screen.
`walk.mjs` asserts each one against the address it should reach, because a redirect that sent
everything to the springboard would render fine and be useless.

## The CSS, and the mistake worth recording

Export's `global.css` restyles `body`, `button`, `a`, `table`, `h1`–`h5`, `ul`, `ol` and
`:focus-visible` at the element level. Loaded as-is it would reach every Core and Shared screen: MUI
buttons would lose their own font and colour, MUI's focus ring would be replaced, and every table in
eleven Shared modules would be restyled. So `src/export/export-scoped.css` carries the same rules
confined to `.cots-export`, the wrapper `ExportPageFrame` puts around Export's pages.

**The first version of that file was scoped with a plain descendant selector, and it broke Export.**
`.cots-export a { … }` confines the rule but raises its specificity from (0,0,1) to (0,1,1), so it
started beating Export's own class rules — `.rtab { color: var(--c-on-brand-muted) }` is (0,1,0), and
the sourcing tab strip rendered in link blue on its dark band, close to illegible. The fix is
`:where(.cots-export)`, which matches without contributing specificity: the cascade inside Export is
exactly what it is standalone, and nothing outside the wrapper is reached.

It was caught by looking at the screen and then measuring the computed colour, not by reading the
diff. Worth remembering the next time a stylesheet is scoped.

## One configuration change

`tsconfig.json` targets **ES2022**, up from ES2020, because the Export contribution targets ES2023 and
uses `Array.prototype.at`. Core and Shared are unaffected: a higher lib only adds declarations.

## What the v1.3 work became

None of it was wasted, and most of it got better by moving:

- the **twenty-three-phase model** is unchanged, and its `path` values — which were always Export's
  own routes — are now the application's routes directly, so the indirection is gone;
- the **phase strip** (breadcrumb, position in the twenty-three, previous and next, the phase context
  panel with its fields, statuses, capabilities and open questions) now sits above a *real* Export
  screen instead of above an iframe, in `ExportPageFrame`;
- `phaseForPath()` is new: the frame works out the phase from the address, longest match wins, which
  is the rule Export's own navigation model uses for the same problem;
- `exportTarget.ts` lost the mode toggle, `exportUrl`, `exportBase`, `PORTABLE_RELATIVE`, `DEV_SERVER`
  and `sameOrigin` — none of them can mean anything now — and kept the destination list and resolver,
  which the redirect needs;
- `integration/ExportScreen.tsx`, the bridge itself, is deleted.

## What was checked

- **`npx tsc -b`** — clean, with Export's 66 source files now compiling into this application.
- **`npm run build`** — clean. 1,279 modules, up from 1,227.
- **`node walk.mjs`** —
  - **255 of 255 routes** render with no console error, up from 186. The new 69 are the Export
    screens, walked for the first time: until now the check inspected the wrapper around the frame
    and never its contents.
  - **10 of 10 module-access cases**, up from 6. The four new ones prove the Export gate covers the
    screens *at their own addresses* — an account without Export scope reaching `/contracts` or
    `/sourcing/funds` would be a real leak, and it is now tested rather than assumed.
  - **10 of 10 redirects** land on the screen they always did.
  - **3 of 3 menus** by privilege; **4 of 4** model comparisons, including 69 model paths checked
    against this application's own route table.
- **In a browser** — no `<iframe>` on any Export screen; the Core app bar above and the Export screen
  below it; the phase strip resolving to the right phase on each; Export's own styling intact after
  the `:where()` fix.

## Still open

1. **The Export exceptions queue is still linked rather than merged** into the one Actions Inbox.
   That is now a business question about three task models, not a technical limit.
2. **The Core role → Export role mapping is still unconfirmed.** Core has seven roles, Export's model
   has ten. The mapping is the one v1.1 wrote, it still lives in `integration/session.ts`, and it is
   still a business confirmation.
3. **Two Core files now differ from the delivered prototype** — `pages/Login.tsx` and
   `layouts/AppShell.tsx`, from the two changes made after v1.3. Export and Shared are untouched.
