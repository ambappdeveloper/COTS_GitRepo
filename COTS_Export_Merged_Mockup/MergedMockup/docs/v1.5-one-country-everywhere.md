# Integrated mockup v1.5 — one country, and it reaches every country

**Date** 30 August 2026
**Status** Draft for review. Not approved.

---

## What was reported

Two observations from the review, a few minutes apart:

> why my country in header Ethiopia and inner screen Sudan

> it changes only between sudan and ethiopia, but not other country — change should apply if i change
> to any country

They look like one bug. They are four, stacked, and only the first was visible.

## The four

**1. Two countries, in two places.** Core and Shared each kept their own active country and never
spoke. The Core header switched `activeCountry`; the Shared store stayed on the `useState('Sudan')` it
was initialised with. So the header said Ethiopia and the Master Plan List said Sudan — under a panel
captioned *"Master plans for the active country"*. Three statements about one country, two of them
wrong.

Fixed at v1.4 by `src/integration/CountrySync.tsx`: Core is the source of truth, and its answer is
pushed into the Shared store whenever it changes, through Shared's own `setCountry` so its cascade
still runs. No Shared file is modified — it is a subscriber, not a patch.

**2. The push was conditional, and the condition was wrong.** The first version of `CountrySync`
refused to push a country the Shared prototype had no records for, reasoning that emptying every
Shared screen was worse than a stale one. That is what produced the second report: the switch worked
between Sudan and Ethiopia and silently did nothing anywhere else.

It was the wrong call. **A country is the scope the session is working in; whether records exist
inside that scope is a different fact.** The right way to say "there are none" is an empty screen, not
another country's records. The country is now pushed unconditionally, and whether this prototype holds
anything for it is reported separately, as a statement rather than a warning.

**3. A screen that threw, and took the application with it.** With the country finally reaching every
value, `pages/S05/ServiceRequestAndShunting.tsx` threw:

```ts
const cm = COUNTRY_MODELS.find((c) => c.country === country)!;   // three rows
…
if (!cm.usesServiceRequest) {                                    // TypeError
```

A non-null assertion over a three-row table. Standalone it holds, because the Shared prototype's own
country selector offers exactly those three countries. Here the country comes from the Core session,
which offers four.

An unguarded `undefined` in a React render does not fail politely — it unmounts the whole tree. So
this was not one broken screen. It was a white page, and **every screen visited afterwards blank until
the browser was reloaded**: the first sweep of the 54 Shared routes under Tanzania reported 24 of 54
rendering, and 29 of those 30 failures were healthy screens standing behind a dead root.

**4. The season inherited from the country before it.** Shared's `setCountry` re-selects the new
country's open season *if it finds one*, and leaves the previous `seasonId` alone if it does not:

```ts
setCountry: (c) => { setCountry(c); const s = SEASONS.find(…); if (s) setSeasonId(s.id); }
```

Standalone that can never bite. Here it meant a country with no seeded season kept pointing at the
previous country's, and S01's landing screen prints it straight out — `01-Nov-2025 – 31-Aug-2026`,
Sudan's season, under a Tanzania heading, beside a trace note saying *COTS identifies the applicable
season from the active country*. Defect 1 again, one level down, and it would have survived the fix to
defect 1 untouched.

## What was done about 3 and 4

### The S05 country gate is answered from the configuration that owns the question

The missing table rows are **not written by hand**. Core's `COUNTRY_CONTEXT` already answers the only
question the screen asks — it lists, per country, the process steps configured off, and
`'Logistics service request'` is one of the names it uses. Two independent checks say it is the right
source:

- **It agrees with the Shared table everywhere the two overlap.** Sudan: Core lists nothing as
  not-applicable, Shared says the service request is used. Ethiopia: Core lists it as not applicable,
  Shared says it is not used. Two of two.
- **It agrees with the rest of Core.** `mockData/c10.ts` carries the same fact a second way, as the
  step-applicability row `op-logistics-request`, documented *"Sudan only"*. And the Core header already
  tells the person switching country that the logistics service request is hidden in the country they
  are switching to — the application was showing that sentence in the switch dialog and then throwing
  on the screen it describes.

So `vite.config.ts` redirects the resolved module `<shared>/mockData/s05.ts` to
`src/integration/SharedCountryModels.ts`, which re-exports the module untouched and replaces one
export. Shared's own three rows are kept **exactly as Shared wrote them** — its prose is its own — and
a row is derived only for a country Shared has no row for and Core does have configuration for.

This is the integration layer doing the thing it exists for: **C10 owns country configuration, so a
module that lacks a fact about a country gets it from C10 rather than from a second copy.** It is the
same principle as `CountrySync` — one country, held in one place, read by everyone.

A derived row answers `usesServiceRequest` and nothing else. The sentence the screen prints states the
derivation and stops:

> **Not applicable for Tanzania.** Derived from the country configuration (C10 / WF-C10-01 Step 3 —
> process step applicability, per country), which lists the logistics service request among the steps
> configured off in Tanzania. How transportation is arranged in Tanzania is not recorded in the Shared
> or Core prototypes — business confirmation required.

It does not describe how transport is arranged, because neither prototype says, and a plausible
sentence there would be an invented country rule presented as fact. `modes` is empty for the same
reason.

### The season is cleared rather than inherited

`CountrySync` now clears `seasonId` when the country has no seeded season. Nothing can print another
country's dates, because there are none to print.

Three S01 screens genuinely cannot render without a season, and they now say so. That is the honest
outcome and it is a finding, not a workaround: **the Shared prototype holds no season for Tanzania or
Mozambique, and whether those countries are in scope is a business question.** The alternative was to
synthesise a season from Core's `'2025/26 season, Dec–May'`, which would have meant inventing start
and end dates and a status — exactly what §14 of the brief forbids.

### One error boundary above every Shared screen

`src/shell/SharedScreenBoundary.tsx`, mounted on the `SharedArea` route element in `App.tsx`. The
known cases above are *answered* rather than caught; this is for the ones that are not. It holds the
failure inside the one screen, keeps the shell, the menu and the session alive, and names the country
it could not render for. It does not retry, does not substitute another country's data, and does not
present an empty screen as though it had rendered.

**It is above the page, not inside `SharedPageFrame`, and that matters.** The throws worth catching
happen in the page's own body, before the frame is ever reached:

```tsx
export default function Landing() {
  const season = SEASONS.find(…) ?? SEASONS.find((s) => s.country === country)!;  // throws here
  return <AppShell …>                                                             // never reached
```

A boundary in the frame sits below the throw and catches nothing. It was tried there first, and it
silently did not work — 51 of 54, with three screens still blanking. Recorded because it is the
obvious first guess.

## One change to the substitution plugin

`substituteModule` now leaves alone an import made **from** the replacement, not just an import
**of** it. Without that, `SharedCountryModels.ts` importing `@shared/mockData/s05` resolves straight
back to itself. It is what lets a replacement build on the module it replaces rather than restate it —
which is the difference between keeping Shared's three rows verbatim and re-typing them here.

## Three prototype warnings, now visible

The v1.5 walk reports three React development warnings it did not report before, on `/s02/calculator`,
`/s07/reports` and `/origination`. **They are not a regression.** React de-duplicates a development
warning by the component stack that produced it, and the whole walk runs inside one document, so which
route a warning is *attributed* to depends on visit order and on the stack above it. Adding the Shared
boundary changed that stack, and three warnings that had been absorbed elsewhere started being
reported against the screens that actually cause them.

Each was then reproduced alone — fresh browser context, sign in, one navigation, nothing else visited.
All three fire. They are defects in the delivered prototypes, in files this project does not modify:

| Route | What | Whose file |
| --- | --- | --- |
| `/s02/calculator` | `<Chip>` (a `<div>`) inside a `<Typography>` that renders a `<p>` | Shared — `pages/S02/Calculator.tsx` |
| `/s07/reports` | a header row keyed by its own text, where two headers repeat | Shared — `pages/S07/Reports.tsx` |
| `/origination` | a link nested inside another link | Export v2.4 — the origination screen |

`walk.mjs` lists them by name and tolerates only the named warning on the named route: the route must
still render, and any *other* console error on it fails as usual. Remove an entry and the check
tightens again, which is what should happen if a prototype is corrected upstream.

## Still open

1. **Whether Tanzania and Mozambique are in scope for the Shared modules.** The prototype holds no
   season and no records for either. The screens are correctly scoped and empty, three of them say
   they cannot render, and none of that is an answer.
2. **Chad.** The Shared S05 table has a row for it; the Core country list does not have the country.
   One of the two is wrong.
3. **The country and step names are matched as text** across three prototypes — `'Tanzania'`,
   `'Logistics service request'` — rather than through a shared enumeration. It works because the
   spellings happen to agree. That is a fragile agreement and worth confirming.
4. Carried from v1.4: the Export exceptions queue is still linked rather than merged; the Core role →
   Export role mapping is still unconfirmed; and **two Core files now differ from the delivered
   prototype** — `pages/Login.tsx` and `layouts/AppShell.tsx`.
